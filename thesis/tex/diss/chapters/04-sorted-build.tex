\chapter{Построение обобщённого дерева поиска сортировкой}
\label{ch:sorted-build}

\section{Постановка}

Построение индекса последовательной вставкой~\eqref{eq:build-insert} не
использует того, что при построении весь набор данных известен заранее. Для
B-дерева это давно учтено: индекс строится сортировкой и заполнением страниц
подряд. Перенос приёма на обобщённое дерево поиска наталкивается на
принципиальное препятствие: интерфейс класса операторов не содержит порядка.
Он содержит операции \code{consistent}, \code{union}, \code{penalty},
\code{picksplit}~--- ни одна из них не задаёт линейного порядка на множестве
ключей, и для большинства индексируемых типов (прямоугольники, многоугольники,
сигнатуры) естественного линейного порядка не существует.

Ключевое наблюдение состоит в том, что для построения дерева \emph{полный}
порядок и не нужен. Достаточно порядка, сохраняющего локальность: если близкие в
смысле индексируемого пространства объекты оказываются близкими в
последовательности, то последовательное заполнение страниц даёт компактные
ключи. Какой именно порядок обладает этим свойством~--- знает не ядро дерева, а
класс операторов.

\section{Интерфейс поддержки сортировки}

Предложено расширить класс операторов необязательной функцией поддержки
сортировки, задающей компаратор. Если функция определена, построение индекса
выполняется по схеме:

\begin{enumerate}
\item все индексируемые значения преобразуются в ключи и сортируются заданным
      компаратором внешней сортировкой;
\item листовые страницы заполняются подряд до заданного коэффициента заполнения;
\item для каждой заполненной страницы формируется элемент вышележащего уровня
      с ключом \code{union} от её содержимого;
\item процедура повторяется по уровням до образования корня.
\end{enumerate}

Существенно, что порядок объявляется в классе операторов, а не в параметрах
индекса. В первой редакции работы компаратор передавался через параметр
отношения, что позволяло указать произвольную функцию с подходящей сигнатурой~---
то есть построить заведомо некорректный индекс. Перенос в класс операторов
делает выбор порядка частью определения типа индекса и допускает проверку при
создании индекса.

Реализация: \commit{16fa9b2b30a}{Add support for building GiST index by
sorting} (выпуск~14); проверка соответствия функции классу операторов~---
\commit{6f0bc5e1daf}{Fix missing validation for the new GiST sortsupport
functions}.

\section{Порядок, сохраняющий локальность}

Для точечного типа в качестве такого порядка использован Z-порядок (код
Мортона): координаты приводятся к целочисленному представлению, и биты
координат чередуются:

\begin{equation}
\label{eq:zorder}
Z(x_1,\dots,x_D) = \sum_{j=0}^{w-1} \sum_{i=1}^{D} b_{i,j} \, 2^{\,jD + i - 1},
\end{equation}

где $b_{i,j}$~--- $j$-й бит $i$-й координаты, $w$~--- разрядность координаты.
Z-порядок обладает нужным свойством: точки, близкие в $D$-мерном пространстве,
получают близкие значения $Z$ (обратное, вообще говоря, неверно~--- существуют
пары близких по $Z$ точек, далёких в пространстве; для целей построения дерева
это допустимо, поскольку влияет на качество, а не на корректность).

Два обстоятельства реализации заслуживают упоминания.

\emph{Представление чисел с плавающей точкой.} Порядок битов представления
IEEE~754, интерпретированных как целое, согласован с числовым порядком для
неотрицательных значений и обращён для отрицательных. Для целей сохранения
локальности этого достаточно: разрыв возникает только при переходе через ноль.

\emph{Неопределённые значения.} Значения NaN не упорядочены относительно
остальных, и произвольный выбор их места в порядке приводит к несогласованности
с семантикой \code{union} и \code{consistent}. Требуется явное соглашение,
согласованное с этими функциями.

\section{Правые ссылки при построении снизу вверх}

При построении сортировкой конкурентного доступа к строящемуся дереву нет:
поиск и расщепление страниц в это время невозможны. Формально это означает, что
правые ссылки, введённые схемой Корнакера \cite{kornacker1997concurrency} для
корректности конкурентного поиска, можно не устанавливать.

Тем не менее они устанавливаются: \commit{265ea567852}{Set right-links during
sorted GiST index build}. Причина~--- в требовании верифицируемости: полнота
цепочки правых ссылок на каждом уровне является структурным инвариантом,
проверяемым средствами главы~\ref{ch:verification}. Индекс, построенный
сортировкой, не должен отличаться от построенного вставкой по набору
выполняющихся инвариантов, иначе средство проверки будет вынуждено различать
способы построения. Это общий принцип: оптимизация не должна сокращать
множество проверяемых свойств структуры.

\section{Перекрытие нелистовых ключей}
\label{sec:overlap-fix}

\subsection{Проблема}

Наивная схема построения заполняет страницу до коэффициента заполнения и
переходит к следующей, то есть выбирает точки разбиения по единственному
критерию~--- использованию места на странице. Для одномерного случая это
оптимально. Для многомерного~--- нет: Z-порядок сохраняет локальность лишь
приближённо, и разбиение по границе страницы может рассечь плотный кластер
точек так, что ключи двух соседних страниц окажутся сильно перекрывающимися.

Согласно~\eqref{eq:point-steady}, качество разбиения входит в стоимость поиска
постоянным множителем на каждом шаге спуска. Измерение
(§\ref{sec:eval-overlap}) даёт для разбиения по заполнению страницы
установившееся перекрытие $\omega_\infty \approx 4{,}0$ при том, что построение
вставкой~--- та планка, которую сортированное построение должно
воспроизвести,~--- даёт $\omega_\infty \approx 1{,}05$. Точечный запрос при
наивной сборке спускается примерно в четыре поддерева на каждом уровне вместо
одного. Индекс строится в 6,8--8,0 раза быстрее и занимает на треть меньше
места, но отвечает на запросы в 2,4--2,5 раза дороже. Именно это делает наивную
сортированную сборку неприемлемой для промышленного применения и объясняет,
почему приём, известный для R-деревьев, долго не переносился в обобщённое
дерево поиска.

\subsection{Алгоритм}

Предложено выбирать точки разбиения не по заполнению страницы, а той же
функцией \code{picksplit}, которая используется при расщеплении переполненного
узла, то есть тем самым критерием качества, который заложен в класс операторов:

\begin{enumerate}
\item накапливать элементы уровня в буфере объёмом в четыре страницы;
\item применять к буферу \code{picksplit} рекурсивно, пока каждая часть не
      помещается на страницу;
\item записывать полученные части как страницы уровня.
\end{enumerate}

Буфер в четыре страницы~--- компромисс: он достаточно велик, чтобы алгоритм
разбиения мог выбрать точку разреза, не совпадающую с границей страницы, и
достаточно мал, чтобы стоимость разбиения оставалась приемлемой. Ограничение
метода прямо следует из этого выбора: алгоритмы разбиения с суперлинейной
сложностью деградируют при четырёхкратном увеличении объёма обрабатываемых
данных. Для классов операторов с такими алгоритмами поддержка сортированного
построения не включается~--- сначала требуется улучшить их \code{picksplit}.

Реализация: \commit{f1ea98a7975}{Reduce non-leaf keys overlap in GiST indexes
produced by a sorted build} (выпуск~15).

Существенно, что алгоритм устраняет не весь штраф, а его бо́льшую часть:
87--89\,\% по измерениям §\ref{sec:eval-overlap}. Остаточные 11--13\,\%~---
цена того, что точки разбиения выбираются в пределах буфера, а не глобально по
всему уровню. Полное восстановление качества потребовало бы просмотра уровня
целиком, что вернуло бы стоимость построения к порядку стоимости построения
вставкой и лишило бы метод смысла. Компромисс формулируется так: за 11--13\,\%
качества дерева метод возвращает ускорение построения в 3,0--3,5 раза
относительно построения вставкой.

\section{Отвергнутые варианты решения}
\label{sec:rejected-alt}

Опубликованный след изменения в открытой системе показывает принятое решение и
не показывает отвергнутых. Между тем именно они позволяют судить, было ли
решение выбором или единственным пришедшим в голову вариантом. Ниже~---
варианты, рассмотренные рабочей группой в декабре 2021~--- январе 2022~года
(Д.~Пролесковский, А.~Каленик, С.~Шулбаков, А.~Бородин, А.~Коротков).

\subsection{Происхождение задачи}

Задача пришла из эксплуатации, а не из анализа. Сортированное построение уже
входило в выпуски, когда П.~Рэмзи измерил самосоединение на PostGIS по
построенному новым способом индексу и получил двукратную деградацию,
опубликовав в ноябре 2021~года в списке postgis-devel изображения дерева до и
после. Анализ §\ref{sec:overlap-fix} написан, чтобы объяснить уже существовавшую
жалобу.

\subsection{Упорядочение листовых элементов по ссылке на строку}

Предлагалось упорядочить элементы листовой страницы по физическому положению
адресуемой строки, чтобы обращения к таблице шли по возрастанию номеров блоков.
Вариант реализован и измерен: различие неотличимо от шума~--- 5,65 против
5,70~с на геометрических данных, причём знак различия менялся между прогонами,
и в пределах 100~мс на намеренно перемешанной таблице. Причина в том, что
первая половина самосоединения и без того обходит таблицу в порядке диска.
Вариант отвергнут как не дающий эффекта.

\subsection{Выбор точки разреза по штрафу вместо \code{picksplit}}

Конкурирующее предложение: набрать половину страницы, а затем для каждого
следующего элемента запрашивать у класса операторов \code{penalty} добавления и
начинать новую страницу, как только штраф станет положительным. Вариант
реализован и по процессорной стоимости дешевле вызова \code{picksplit} на
буфере.

Он не принят, и довод против него не в производительности, а в происхождении
критерия. Функция \code{picksplit}~--- это место, где автор класса операторов
уже выразил, что для его типа ключа считается хорошим разбиением; порог по
штрафу есть критерий, придуманный нами и навязанный всем типам ключей.
Принятое решение дороже по построению, и это плата за переиспользование чужого
критерия качества вместо изобретения своего.

\subsection{Раздельный коэффициент заполнения для внутренних страниц}

Наблюдение, сделанное при разработке: на число уровней и на число ключей
промежуточных уровней влияет прежде всего число \emph{листовых} страниц,
поскольку элемент следующего уровня есть объединение всех элементов страницы
предыдущего, а несколько нисходящих ссылок на одну страницу невозможны~---
ссылка адресует страницу целиком.

Отсюда следовало объяснение, конкурирующее с предложенным в
§\ref{sec:overlap-fix}: индекс, построенный вставкой, отвечает быстрее не
из-за меньшего перекрытия, а из-за большего числа листовых страниц. Объяснение
проверено контрольным опытом (§\ref{sec:eval-overlap}) и для числа обращений к
страницам индекса не подтвердилось; для времени самосоединения по полигонам,
где доминирует перепроверка, оно остаётся верным. Это разные составляющие
стоимости, и их следует различать.

\subsection{Бюджет свободного места, передаваемый вверх по дереву}

Предлагалось считать коэффициент заполнения свойством индекса, а не страницы:
при сбросе страницы пересчитывать отклонение от заданного заполнения в байтах и
передавать этот бюджет вверх, так что недозаполнение листа разрешает
переполнение родителя. Суммарное свободное место сохраняется, но размещается
там, где оно полезнее. Вариант не реализован и не опровергнут; направление
оставлено открытым.

\section{Специализация компараторов}

Стоимость~\eqref{eq:build-sort} определяется числом сравнений, умноженным на
стоимость одного сравнения. Последняя для обобщённой реализации включает
косвенный вызов функции сравнения. Специализация компаратора для конкретного
типа~--- подстановка тела функции сравнения в код сортировки~--- устраняет эти
накладные расходы. Результаты: \commit{53d3daa491b}{Specialize intarray sorting}
и \commit{30229be755e}{Simplify SortSupport for the macaddr data type}.

\section{Границы применимости}
\label{sec:sorted-limits}

Метод применим, если для класса операторов существует порядок, сохраняющий
локальность, и алгоритм разбиения не деградирует при увеличении объёма входа.
Практическую проверку этих условий даёт история распространения метода на
классы операторов расширения \code{btree\_gist}, реализующего индексирование
скалярных типов средствами обобщённого дерева поиска.

Первая попытка (2021) была отозвана в тот же день из-за отказов на сборочной
ферме: обнаружились как ошибка в тестовом окружении, так и содержательная
ошибка~--- компаратор для битовой строки использовал сравнение, не согласованное
с семантикой типа. Возврат состоялся четырьмя годами позже, реализацией,
написанной заново: \commit{e4309f73f69}{Add support for sorted gist index builds
to btree\_gist} (выпуск~18), где сортированное построение стало способом по
умолчанию.

Этот эпизод~--- содержательный материал, а не курьёз. Он показывает, что
корректность сортированного построения целиком определяется согласованностью
компаратора с остальными функциями класса операторов, и что проверить эту
согласованность внешними средствами затруднительно: несогласованный компаратор
даёт корректно выглядящий индекс, теряющий часть ответов. Отсюда прямая связь с
главой~\ref{ch:verification}: инвариант <<ключ родителя покрывает ключи
потомков>> нарушается при несогласованном компараторе и обнаруживается проверкой
структуры.

\section{Экспериментальная оценка}

Первоначальное измерение 2019 года, послужившее основанием для работы: построение индекса
над тремя миллионами случайных точек заняло 32,1~с при построении вставкой и
6,1~с при построении сортировкой (выпуск~13, конфигурация по умолчанию); при
этом объём индекса существенно сократился, а время выполнения запросов осталось
прежним.

Это измерение относится к первой редакции и приводится как исходная мотивация.
Итоговые измерения~--- в главе~\ref{ch:evaluation}, с обязательным контролем
перекрытия нелистовых ключей и времени выполнения запросов, а не только времени
построения.

\section{Выводы по главе}

\begin{enumerate}
\item Задача построения обобщённого дерева поиска сводится к сортировке, если
      порядок, сохраняющий локальность, объявляется классом операторов через
      интерфейс поддержки сортировки; это делает приём применимым к
      произвольному классу операторов.
\item Наивное сортированное построение увеличивает перекрытие нелистовых ключей
      и замедляет поиск; выбор точек разбиения функцией \code{picksplit} над
      буфером в четыре страницы устраняет этот эффект.
\item Правые ссылки устанавливаются при построении, хотя конкурентности нет,~---
      ради сохранения полного набора проверяемых инвариантов.
\item Корректность метода определяется согласованностью компаратора с
      остальными функциями класса операторов и должна проверяться средствами
      верификации структуры.
\end{enumerate}
