\chapter{Алгоритмы повышения ветвистости и снижения перекрытия ключей}
\label{ch:fanout}

Согласно~\eqref{eq:fanout}, ветвистость узла определяется размером ключа $k$ и
размером сопутствующих служебных данных $\sigma$. В этой главе рассматриваются
три источника избыточности, каждый из которых увеличивает $k$ или $\sigma$ без
пользы для поиска, и алгоритмы их устранения; затем~--- способ снять
зависимость стоимости просмотра узла от его ветвистости.

\section{Избыточные представления ключа}
\label{sec:compress}

\subsection{Постановка}

Интерфейс класса операторов обобщённого дерева поиска исторически требовал двух
парных функций: \code{compress} преобразует индексируемое значение во
внутреннее представление ключа, \code{decompress}~--- обратно. Замысел состоял
в том, чтобы хранить в дереве сжатую форму значения: например, для многоугольника~---
его ограничивающий прямоугольник.

Однако для значительной части классов операторов преобразование не требуется:
внутреннее представление совпадает с внешним. Реализация вынуждала и в этом
случае определять функции, выполняющие тождественное преобразование. Помимо
избыточного кода это имело два следствия:

\begin{enumerate}
\item ядро дерева не знало, совпадает ли хранимое представление с исходным
      значением, и потому не могло выполнить индексное сканирование без
      обращения к таблице, если класс операторов не определял ещё и функцию
      \code{fetch};
\item тождественная функция \code{decompress} вызывалась для каждого элемента
      каждой просмотренной страницы, то есть $O(f)$ раз на узел.
\end{enumerate}

\subsection{Решение}

Предложено сделать обе функции необязательными и придать их отсутствию
семантику. Если \code{compress} не определена, ядро дерева знает, что хранимое
представление тождественно исходному значению, и:

\begin{itemize}
\item выполняет индексное сканирование без обращения к таблице, не требуя
      функции \code{fetch};
\item не вызывает преобразование при просмотре узла.
\end{itemize}

Реализация: \commit{d3a4f89d8a3}{Allow no-op GiST support functions to be
omitted} (выпуск~11). Помимо снижения накладных расходов результат сокращает
объём обязательного кода класса операторов~--- это существенно для
расширяемости, поскольку порог входа для разработчика нового метода доступа
определяется именно объёмом обязательной обвязки.

\section{Покрывающие атрибуты}
\label{sec:include}

\subsection{Постановка}

Индексное сканирование без обращения к таблице возможно, если все запрашиваемые
столбцы присутствуют в индексе. Наивный способ добиться этого~--- включить
дополнительные столбцы в состав ключа. Для обобщённого дерева поиска он
неприменим по двум причинам: во-первых, для типа дополнительного столбца может
не существовать класса операторов; во-вторых, включение столбца в ключ
увеличивает $k$ на \emph{всех} уровнях дерева, а согласно~\eqref{eq:fanout}
и~\eqref{eq:height} это снижает ветвистость внутренних узлов и увеличивает
высоту дерева.

\subsection{Решение}

Предложено разделить атрибуты индекса на ключевые и покрывающие. Покрывающие
атрибуты хранятся только в листовых страницах, не участвуют в навигации, не
входят в ключи внутренних узлов и не требуют класса операторов для своего типа.
Формально: ветвистость внутренних уровней определяется~\eqref{eq:fanout} с
$k$ по ключевым атрибутам, ветвистость листового уровня~--- с $k+k_{\text{inc}}$;
поскольку по~\eqref{eq:height} высота зависит от ветвистости внутренних узлов,
добавление покрывающих атрибутов её не увеличивает.

Существенное отличие от B-дерева: там покрывающие атрибуты введены
преимущественно для того, чтобы наложить ограничение уникальности на часть
атрибутов индекса, а здесь основной мотив~--- получить индексное сканирование
для атрибутов, тип которых вообще не имеет класса операторов обобщённого дерева
поиска.

Реализация: \commit{f2e403803fe}{Support for INCLUDE attributes in GiST}
(выпуск~12), для дерева с разбиением пространства~---
\commit{09c1c6ab4bc}{Support INCLUDE'd columns in SP-GiST} (выпуск~14).

\section{Модификация элемента на странице}
\label{sec:overwrite}

\subsection{Постановка}

Вставка в обобщённое дерево поиска сопровождается обновлением ключей на пути
спуска: ключ родителя расширяется так, чтобы покрыть вставленный элемент. Каждое
такое обновление~--- модификация элемента, уже находящегося на странице.

В исходной реализации модификация выполнялась как удаление элемента с
последующим добавлением нового в конец страницы. Поскольку элементы на странице
хранятся плотно, удаление вызывает перемещение всей области данных, лежащей
<<ниже>> удаляемого элемента. Кроме того, недавно обновлённые элементы всегда
оказывались в конце страницы, что разрушало соответствие между порядком
указателей и физическим порядком данных и ухудшало локальность обращений к кэшу
процессора.

\subsection{Решение}

Предложена операция перезаписи элемента на месте. Если размер нового элемента
равен размеру старого~--- а при обновлении ключа это типичный случай,~--- данные
на странице не перемещаются вовсе; при неравенстве размеров перемещается только
разность. Порядок элементов сохраняется.

Реализация: \commit{b1328d78f88}{Invent PageIndexTupleOverwrite, and teach BRIN
and GiST to use it} (выпуск~10). Результат опубликован
в~\cite{borodin2017memory}; там же приведены измерения: сокращение времени
вставки отсортированных данных примерно в три раза и около 15\,\% на случайных
данных, при одновременном уменьшении объёма индекса. Эти значения относятся к
выпуску~10 и подлежат перепроверке на актуальной версии
(глава~\ref{ch:evaluation}).

Отдельного внимания заслуживает побочное следствие, отмеченное при принятии
изменения: физическое содержимое страницы после воспроизведения журнальной
записи стало иным, чем прежде, хотя логически страница эквивалентна. Это пример
общего свойства оптимизаций страничной раскладки~--- они затрагивают
совместимость на уровне побайтового сравнения страниц, что важно для средств
проверки корректности воспроизведения журнала.

\section{Внутристраничное индексирование}
\label{sec:intrapage}

\subsection{Постановка}

Из~\eqref{eq:fanout} и~\eqref{eq:point} следует, что рост ветвистости снижает
число просматриваемых \emph{страниц}, но стоимость обработки одной страницы
растёт линейно по $f$: чтобы отобрать поддеревья для спуска, ядро вызывает
\code{consistent} для каждого из $f$ элементов узла. Обозначив стоимость одного
вызова через $c_c$, получим для точечного запроса

\begin{equation}
\label{eq:intrapage}
T = \sum_{l=0}^{H-1} \omega_l \left( c_r + f\,c_c \right).
\end{equation}

При достаточно большом $f$ и нетривиальной функции \code{consistent} второе
слагаемое доминирует. Это ограничивает осмысленное увеличение размера страницы:
выигрыш от сокращения числа обращений к носителю съедается ростом процессорной
стоимости просмотра узла.

\subsection{Предлагаемый подход}

Разорвать эту связь можно, разместив внутри страницы вспомогательную структуру,
позволяющую отбирать кандидатов для \code{consistent} не за $O(f)$, а за
$O(\log f)$ или за $O(m)$, где $m$~--- число реально пересекающихся с запросом
элементов. Тогда~\eqref{eq:intrapage} принимает вид

\begin{equation}
T' = \sum_{l=0}^{H-1} \omega_l \left( c_r + (m_l + \log f)\,c_c \right),
\end{equation}

и увеличение размера страницы становится безусловно выгодным.

Требования к внутристраничной структуре, вытекающие из ограничений
обобщённого дерева поиска:

\begin{enumerate}
\item структура строится над теми же операциями класса операторов
      (\code{consistent}, \code{union}, \code{penalty}), то есть остаётся
      обобщённой;
\item её перестроение при вставке элемента должно быть дешевле, чем экономия на
      просмотре, иначе выигрыш на поиске оплачивается проигрышем на вставке;
\item структура должна помещаться на той же странице и корректно
      восстанавливаться при воспроизведении журнала;
\item при повреждении структуры результат запроса не должен становиться
      неверным~--- допустима деградация к линейному просмотру.
\end{enumerate}

\subsection{Состояние работы}

Направление обсуждалось в сообществе разработчиков \pg{} (тред <<[WiP] GiST
intrapage indexing>>, 2018) и остаётся незавершённым: предложенные варианты
удовлетворяли требованиям~1 и~3, но не требованию~2 на нагрузках с
преобладанием вставок. Это единственная задача работы, требующая нового кода;
её решение планируется на основе моделей настоящей главы.

\section{Функция штрафа и качество разбиения}
\label{sec:penalty}

Функция \code{penalty} определяет выбор поддерева при вставке и тем самым~---
перекрытие $\omega_l$ из~\eqref{eq:overlap}. Стандартная для R-дерева функция
минимизирует прирост площади ключа, что при многомерных данных приводит к
систематическому предпочтению уже <<раздутых>> ключей. В
\cite{borodin2017penalty} предложена функция штрафа, учитывающая, наряду с
приростом площади, изменение периметра и степень перекрытия с соседними
ключами~--- по мотивам критериев RR*-дерева \cite{beckmann2009rrstar}, но
сформулированная в терминах интерфейса класса операторов.

Результат не был принят в основную ветку \pg{}: изменение функции штрафа меняет
форму уже построенных индексов и потому несовместимо с требованием
неизменности поведения при обновлении версии СУБД без перестроения индексов.
Этот случай показателен: для промышленной СУБД ограничением оказывается не
качество алгоритма, а совместимость. В главе~\ref{ch:sorted-build}
рассматривается путь, свободный от этого ограничения: воздействие на перекрытие
не через функцию штрафа, а через процедуру построения индекса.

Смежный результат~--- корректная обработка неопределённых значений при
сравнении расстояний в очереди приоритетов поиска ближайших соседей:
\commit{e5d8f359610}{Fix handling Inf and Nan values in GiST pairing heap
comparator}.

\section{Выводы по главе}

\begin{enumerate}
\item Отказ от обязательных функций преобразования ключа устраняет избыточные
      вызовы при просмотре узла и позволяет выполнять индексное сканирование без
      обращения к таблице, не требуя дополнительных функций класса операторов.
\item Разделение атрибутов на ключевые и покрывающие позволяет включить в индекс
      столбцы, тип которых не имеет класса операторов, не увеличивая высоту
      дерева.
\item Перезапись элемента на месте устраняет перемещение данных на странице при
      обновлении ключей на пути спуска.
\item Стоимость просмотра узла растёт линейно по ветвистости~\eqref{eq:intrapage},
      что ограничивает выигрыш от роста $f$; снятие этого ограничения требует
      внутристраничной структуры и составляет направление дальнейшей работы.
\end{enumerate}
