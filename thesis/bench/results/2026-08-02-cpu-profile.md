# Куда уходит процессорное время при спуске по GiST

Дата: 2026-08-02. Машина g2. Набор: 10 млн равномерных точек, индекс и таблица
целиком в буферном кэше~--- измеряется процессор, не носитель.

Нагрузка: пространственное соединение 200 тыс. внешних строк с индексом
(2 001 346 строк результата). Один запрос выполняет сотни тысяч спусков по
дереву, поэтому разбор, планирование и работа с каталогом амортизируются.

Первая попытка мерила одиночные запросы через `pgbench`, и до 8 % времени
уходило в парсер SQL, а планировщик к тому же уходил в последовательное
сканирование, потому что `random()` в предикате мешает оценить селективность.
Оба обстоятельства стоит помнить: профиль индексного кода легко подменить
профилем накладных расходов на запрос.

## Профиль, самостоятельное время

| доля | функция | что это |
|---|---|---|
| 22,38 % | `gistScanPage` | цикл по элементам страницы: обход смещений, подготовка элемента, постановка в очередь |
| 14,06 % | `gist_point_consistent` | собственно предикат класса операторов |
| 12,76 % | `hash_search_with_hash_value` | поиск страницы в таблице буферов |
| 10,15 % | `heap_page_prune_opt` | сторона таблицы |
| 6,70 % | `MemoryContextReset` | |
| 5,68 % | `PinBuffer` | |
| 5,43 % | `heap_hot_search_buffer` | сторона таблицы |
| 4,74 % | `FunctionCall5Coll` | вызов предиката через fmgr |
| 3,32 % | `gistcheckpage` | |
| 2,26 % | `gistdentryinit` | подготовка элемента |

Сводка по группам:

- **работа с элементами страницы индекса: 46,8 %**
  (`gistScanPage` + предикат + `FunctionCall5Coll` + `gistdentryinit` + `gistcheckpage`);
- работа с буферами: 18,4 % (`hash_search` + `PinBuffer`);
- сторона таблицы: 15,6 %.

## Выводы

**Механика обхода элементов дороже самого предиката.** `gistScanPage` тратит
22,4 % против 14,1 % у `gist_point_consistent` — в 1,6 раза больше. То есть
основную цену платит не вычисление предиката, а перебор элементов как таковой:
цикл по смещениям, распаковка, постановка в очередь.

**Накладные расходы вызова через fmgr — 4,7 %**, треть от стоимости самого
предиката. Пакетное вычисление предиката (одна опорная функция на массив
ключей вместо вызова на элемент) сэкономит порядка 5 % общего времени. Это
реальный, но не главный выигрыш.

**Главный резерв — сократить число просматриваемых элементов, а не удешевить
их обработку.** Если внутристраничная структура позволит пропускать половину
элементов, экономится половина от 46,8 %, то есть порядка 20 % процессорного
времени серверного процесса. Это на порядок больше, чем даёт пакетный вызов, и
это ровно то направление, которое было заявлено в работе 2019 года и не прошло
в основную ветку из-за вмешательства в формат кортежа.

**Снижение перекрытия окупается и по процессору.** Поиск страницы в таблице
буферов плюс закрепление — 18,4 % времени, и обе величины прямо
пропорциональны числу посещённых страниц, то есть $\omega$. Работа по
сортированному построению (P1) до сих пор обосновывалась через ввод-вывод; на
данных, помещающихся в кэш, она даёт ещё и процессорный дивиденд. Это стоит
добавить в статью: двукратное различие $\omega$ означает не только вдвое
меньше чтений, но и вдвое меньше обращений к таблице буферов.

## Что отсюда следует для порядка работ

1. Внутристраничное индексирование, но без изменения формата страницы:
   структура строится при загрузке страницы в буфер и живёт рядом с буфером,
   инвалидируясь при модификации. Возражение 2018 года снимается по построению,
   а выигрыш~--- порядка 20 %.
2. Пакетное вычисление предиката: дёшево в реализации, около 5 %, и укладывается
   в ту же линию «что фреймворк обязан затребовать от класса операторов».
3. Параллельная сортированная сборка: замыкает линию P1
   (порядок → качество разбиения → параллелизм) и закреплена за автором по
   итогам обсуждения в списке рассылки.

## Ограничения

- Один класс операторов (`point_ops`), равномерные данные, один прогон.
- Профиль снят с частотой 999 Гц в течение 20 с.
- Доли зависят от селективности: при более крупных окнах вырастет доля стороны
  таблицы, при более мелких~--- доля навигации по дереву.
