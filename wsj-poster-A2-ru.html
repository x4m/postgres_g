Главная фича · 9 июля · коммит 86ab7f4c721

JSON_TABLE PLAN: сага длиной в четыре года

+2017 / −112 строк · 13 файлов · 7 соавторов · 11 ревьюеров · обсуждение с 2022 года

Александр Коротков

Если у июля есть один флагманский патч — это он. JSON_TABLE приехал в PostgreSQL 17 без клаузы PLAN, и всё это время висел долг перед стандартом SQL/JSON.

Что решает PLAN. JSON_TABLE разворачивает вложенные пути через NESTED PATH. Вопрос: как склеивать строки от нескольких вложенных путей? До июля ответ был зашит наглухо — родитель с детьми через LEFT OUTER, братья между собой через UNION. Теперь это управляется.

              ┌──────────────────────────────┐
              │  row pattern  '$'  AS root   │
              └──────────────┬───────────────┘
                             │ INNER / OUTER  ← родитель↔ребёнок
             ┌───────────────┴────────────────┐
  ┌──────────▼──────────┐         ┌──────────▼──────────┐
  │ NESTED '$.phones'   │  UNION  │ NESTED '$.emails'   │
  │        AS ph        │◄───────►│        AS em        │
  └─────────────────────┘  CROSS  └─────────────────────┘
                             ▲
       братья: UNION (по строке на каждого) ─┘
                или CROSS (декартово произведение)
[ PLAN ( json_table_plan )
| PLAN DEFAULT ( { INNER | OUTER } [ , { CROSS | UNION } ]
               | { CROSS | UNION } [ , { INNER | OUTER } ] ) ]

Отступление от стандарта. SQL/JSON требует: если есть PLAN, то каждый NESTED PATH обязан иметь имя через AS. PostgreSQL решил иначе — безымянным путям имя генерируется автоматически. Но у сгенерированного имени есть цена:

-- работает: PLAN DEFAULT с безымянным NESTED path
SELECT * FROM JSON_TABLE(
    jsonb '[]', '$' AS path1
    COLUMNS ( NESTED PATH '$' COLUMNS ( foo int PATH '$' ) )
    PLAN DEFAULT (UNION)
) jt;

-- упадёт: явный PLAN() ссылается на пути по имени,
-- а сгенерированное имя назвать невозможно
SELECT * FROM JSON_TABLE(
    jsonb '[]', '$' AS path1
    COLUMNS ( NESTED PATH '$' COLUMNS ( foo int PATH '$' ) )
    PLAN (path1)
) jt;
ERROR:  nested path not covered by the plan

Хроника посадки. Большие патчи не приземляются чисто. За две недели следом: забытый catversion bump; откат каскадирования ON ERROR; потерянные скобки при deparse вложенных join'ов; столкновения автоимён путей; правка документации; устранение повторного вычисления вложенных путей; удаление недостижимой проверки ошибки. Итого 12 коммитов месяца с «JSON» в заголовке — классическая кривая посадки большой фичи.

Вторая полоса · 2 июля · коммит a5918fddf10

Конфликты репликации — теперь в таблице

+1451 / −40 строк · 31 файл

Амит Капила

Раньше конфликт логической репликации отправлялся в postgresql.log простым текстом. Хочешь проанализировать — парси логи регулярками. Теперь конфликты можно писать в таблицу.

CREATE SUBSCRIPTION sub
  CONNECTION 'host=pub dbname=app' PUBLICATION pub
  WITH (conflict_log_destination = 'table');
  --  'log' | 'table' | 'all'
   apply worker
        │  обнаружен конфликт
        ▼  (insert_exists / update_origin_differs / …)
  ┌────────────────────────────┐
  │  conflict_log_destination  │
  └──────┬──────────────┬──────┘
     'log'│              │'table'
         ▼              ▼
  postgresql.log   схема pg_conflict (системная)
                   └── pg_conflict_log_<subid>
                         ▲ internal dependency
                   DROP SUBSCRIPTION → таблица исчезает

Схема журнала — прямо из ConflictLogSchema[]:

{"relid",OID} {"schemaname",TEXT} {"relname",TEXT}
{"conflict_type",TEXT} {"remote_xid",XID}
{"remote_commit_lsn",LSN} {"remote_commit_ts",TIMESTAMPTZ}
{"remote_origin",TEXT} {"replica_identity_full",BOOL}
{"replica_identity",JSON} {"remote_tuple",JSON}
{"local_conflicts",JSONARRAY}

Обратите внимание: json, а не jsonb. Комментарий в коде объясняет выбор прямо — это точный аудиторский снимок, а jsonb его нормализовал бы: переупорядочил ключи, схлопнул дубликаты, потерял форматирование чисел. Искать по кортежам никто не собирается; индексируют скалярные колонки, а json-поля — payload для разбора постфактум.

Таблица под замком. Запрещено: ALTER, DROP, CREATE INDEX, триггеры, правила, политики, расширенная статистика, наследование, использование как FK-цель, а также INSERT, UPDATE, MERGE и блокировка строк вручную. Разрешено ровно два действия — DELETE и TRUNCATE, чтобы чистить старьё.

Плюс: таблицы конфликтов исключены из публикаций, даже из FOR ALL TABLES. Иначе — весёлый бесконечный цикл.

Коммит a32733d8f10, Том Лейн, 17 июля. Фича, позволявшая писать GROUP BY ALL вместо перечисления неагрегатных выражений, откачена — причём из ветки 19 тоже (Backpatch-through: 19).

ef38a4d9756  «Add GROUP BY ALL»            ← жизнь
2ce745836    «comment improvements»
    …
a32733d8f10  Revert "Add GROUP BY ALL"     ← смерть

Причина, из коммит-сообщения: постревью обнаружило, что GROUP BY ALL не учитывал специальную обработку элементов, которые заодно фигурируют в ORDER BY. Запрос возвращал неверные результаты, когда ORDER BY задаёт нестандартную семантику равенства.

Чинится рефакторингом — но «too much code churn for late beta». Классический постгресовый расклад: неправильные результаты плюс поздняя бета равно откат, без обсуждений.

Репортёр — Chao Li. Обещание «We'll revert and try again in v20» лежит на столе. Строчкой ниже в июльском логе — коммит Update GROUP BY ALL comments about window functions от 8 июля, попавший в дерево за девять дней до похорон.

Блокировки по бэкендам

Из 39 коммитов Паке львиная доля — про pgstat. Всего 25 коммитов месяца трогают статистику.

8c579bdc366 (автор — Бертран Друво). Была pg_stat_lock, общая по кластеру. Стала ещё и персональная:

SELECT a.pid, a.state, l.locktype, l.waits,
       l.wait_time, l.fastpath_exceeded
FROM   pg_stat_activity a
CROSS JOIN LATERAL pg_stat_get_backend_lock(a.pid) l
WHERE  l.waits > 0
ORDER BY l.wait_time DESC;

fastpath_exceeded — сколько раз бэкенд вылетел за пределы fast-path блокировок. В том же месяце Паке дописал в документацию целый новый раздел про fast-path locking. Читать вместе.

Штрих для перфекционистов: stat_lock.wait_time за месяц дважды меняли тип — сначала на double precision, потом чинили потерю точности в pg_stat_us_to_ms(), потом ловили там опечатку. Микросекунды в миллисекунды оказались сложнее, чем выглядят.

Мелочи, которые порадуют

min() и max() для uuid. У типа uuid давно был полный набор операторов сравнения и btree-класс — то есть он полностью упорядочен. Не хватало только агрегатов. Добавили uuid_larger() и uuid_smaller(). Красивая деталь из коммит-сообщения: значения сравниваются лексикографически по всем 128 битам, а у UUIDv7 старшие биты — это Unix-timestamp. Значит min()/max() по UUIDv7 честно возвращают самое старое и самое новое значение.

Имена индексов на выражениях стали осмысленными — два коммита Тома Лейна. Мелочь, но её ждали годами.

Предупреждение про MD5. Аутентификация паролем с MD5-хешем теперь выдаёт warning. Сам MD5 не удалили — но намекнули очень прозрачно.

psql: роль pg_read_all_stats наконец видит размер базы в \l+; починено автодополнение \df для процедур; исправлен выбор пейджера для перенесённого расширенного вывода.

pg_recvlogical шлёт финальный feedback при SIGINT/SIGTERM — больше не теряется прогресс при аккуратной остановке.

Возвращение префиксных операторов. Коммит 2f094e7ac сделал | и -> встроенными именами операторов, корректно дав им приоритет и добавив инфиксные продукции — но забыл про префиксные. Как минимум одно расширение на это рассчитывало. Bug #19558, репортёр — Пьер Сенелляр.

Закрытые уголки синтаксиса: запрещены set-returning функции внутри OVER; запрещено переименование правила в _RETURN; io_min_workers больше io_max_workers теперь выдаёт warning.
